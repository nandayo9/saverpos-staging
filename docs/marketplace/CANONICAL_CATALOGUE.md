# Canonical marketplace catalogue — staging foundation

This additive catalogue unifies historical Trade-In model/variant IDs with public marketplace identity. It does not own inventory, prices, payments or accounting. User scope is local/staging only; inventory examples remain explicitly synthetic. No production deployment is authorized.

`CanonicalDeviceCatalogue` is called by the existing `IntelligenceService` VARIANT importer. Category + case/whitespace-normalized brand/model/generation form the model identity. The model’s public slug is stable. Exact specification hashes and native variation mappings cannot be reassigned silently. Native business ownership is checked by the importer; the staff controller also checks its existing approval permission and variation scope. Device IDs and historical listing fields are unchanged.

Models start DRAFT. Use the existing importer with kind `CATALOGUE_MODEL`, target equal to the historical `model_id`, and data containing `expected_revision`, `publication_state` (DRAFT/PUBLISHED), `synthetic` (boolean), `review_reference`, `summary`, `configuration_guidance`, `condition_guidance`. PUBLISHED requires at least 80 plain-text characters in each content section. Reimporting a VARIANT is idempotent at the mapping level and still appends governed evidence. Publication is not permission to index or activate feeds.

Apply migration `2026_09_08_000003_create_canonical_device_catalogue.php` after a verified private staging DB backup. The staging bootstrap now enforces the backup when either new evidence/catalogue table is missing. Before importing historical records, execute `php scripts/canonical-catalogue-dry-run.php BUSINESS_ID` with staging environment configuration. It always rolls back; an ambiguity exits 2. Any ambiguity invalidates approval of the whole candidate set. Do not interpret first-seen order as authoritative mapping. The bounded dry-run refuses 5,000 evidence records rather than silently claiming complete coverage.

Validation on 8 September 2026: a newly created isolated `saverpos_demo_marketplace_20260908` MySQL database applied all migrations. Two deliberately conflicting dummy legacy records generated one trial map and one normalized duplicate-identity rejection. Both new tables contained zero rows after rollback. The feature suite checks permanent models after sale, public status privacy, duplicate/specification rejection, source authorization, valuation and native acquisition. Hosted legacy data mapping is not established by that disposable test.

Public source endpoints retain `/customer-projection/v1` token/cohort guards. The added `/devices/{publicDeviceId}/status` exposes only public identity/model/state for eligible previously published devices. Sold/reserved data never appears as available inventory. Model/specification pages can survive zero stock. Existing historical model slugs resolve to the current canonical model; the website performs a 301 to its canonical path.

Rollback: use the prior reviewed application release and preserve the additive catalogue/evidence tables. Do not drop mapped identities or rewrite stock to undo this feature. A DB restore requires its own scoped recovery decision and verified private snapshot.

Limitations: no source mappings are automatically applied on deployment; no real inventory is certified; no source/pricing/ML gates are enabled. Source listing validation scans the filtered staging cohort before pagination; production scale requires profiling/materialized projection work. Native reservation/online checkout, production feed activation and full hosted source-mode acceptance remain outside this release’s completed behavior.
