# RCR-007 — Provider Repair Containment Audit

**Audit date:** 2026-08-28  
**Scope:** supplied UltimatePOS 7.3 checkout only; no PHP runtime, database, browser, or production deployment was accessed.  
**Status:** `STATIC AUDIT COMPLETE — RUNTIME CONTAINMENT NOT YET PROVEN`

## 1. Decision

SaverBro will not use the unavailable provider `Modules/Repair` module as the
writable Repair authority. The owned Repair domain will be built under
`Modules/Recommerce` and will use the canonical Recommerce Device.

Provider Repair recovery is not required to build new SaverBro Repair
capability. It remains relevant only if a live deployment contains legacy
Repair jobs, files, permissions, routes, or transaction history that must be
preserved, migrated, or archived.

## 2. Static findings

| Area | Finding | Consequence |
|---|---|---|
| Provider source | `Modules/Repair` is absent. | The provider cannot be treated as an available dependency or implementation base. |
| Compiled cache | `bootstrap/cache/repair_module.php` names `Modules\\Repair\\Providers\\RepairServiceProvider`. | Cache may be stale and must be cleared/regenerated only during controlled runtime work. |
| Public assets | `public/modules/repair/js/app.js` and `sass/app.scss` are zero bytes. | Provider frontend capability is not proven. |
| Status/config | `modules_statuses.json` still has `Repair: true`; `SHOW_REPAIR_STATUS_LOGIN_SCREEN` defaults true. | Status and flags must not be used as proof of a live provider module. |
| Core PHP coupling | `SellPosController` and `TransactionUtil` reference provider controllers/entities for Repair sales, receipts, redirects, and status/model data. | The owned module must avoid provider routes/classes and must add compatibility tests before changing these paths. |
| Blade coupling | Layouts, invoice settings, brand screens, and return views reference `repair::` namespaces or provider-specific fields. | Provider-dependent views need an explicit disabled/legacy fallback policy. |
| Seed/schema coupling | Dummy seed data references `repair_device_models`, `repair_statuses`, `repair_model_id`, and `repair_module`. | Seed intent is not production schema evidence; no new owned schema should reuse these names without an approved mapping. |
| Recommerce boundary | `Modules/Recommerce` contains no provider Repair integration. | This is the correct boundary for new owned Repair work. |

## 3. Required containment work

1. Run the application baseline with provider Repair disabled and stale module
   cache removed or regenerated by the deployment owner.
2. Prove Laravel boot, route discovery, migrations, and ordinary POS flows do
   not require provider classes when the provider is disabled.
3. Decide how legacy provider-specific receipts, views, and transaction rows
   behave when encountered: read-only compatibility, neutral fallback, or
   separately approved migration/archive.
4. Keep the owned Repair implementation outside legacy
   `transactions.sub_type = 'repair'`, provider tables, provider routes, and
   provider fields until a separate legacy cutover decision exists.
5. Add a regression test that the Recommerce module can boot and operate with
   no `Modules\\Repair` class resolution.

## 4. Owned Repair target

The first owned Repair slice should use:

- `Modules/Recommerce` routes, policies, entities, migrations, views, and tests;
- one shared `repair_jobs` model supporting `INTERNAL_REFURBISHMENT` and
  `CUSTOMER_REPAIR`;
- the canonical Device where a physical device exists;
- Ultimate POS contacts, products/variations, stock utilities, sales,
  adjustments, invoices, payments, and accounting as the existing authorities;
- Recommerce-owned diagnostics, actions, parts reservations, QC, custody,
  timeline, and direct-cost evidence.

## 5. Gate result

The provider dependency is now classified as a **legacy containment risk**,
not a blocker to designing or implementing SaverBro-owned Repair. The runtime
baseline, approved data profile, and browser/POS regression proof remain open.

No provider source was deleted, no cache was modified, no database was changed,
and no module was enabled by this audit.
